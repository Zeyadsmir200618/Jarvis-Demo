# MCP integration — architecture, security model and setup

## What runs where

```
 YOUR PC (host)                                           Docker (compose project "jarvis")
 ───────────────────────────────────────────────          ───────────────────────────────────
 Browser ── http://localhost:3000 ───────────────────────▶ frontend  (Next.js dev server)
         ── http://localhost:8000 ───────────────────────▶ backend   (FastAPI = MCP CLIENT)
                                                                │
 jarvis_mcp_server  (MCP SERVER, Python)  ◀── Streamable HTTP ──┘  http://host.docker.internal:8765/mcp
   │  bearer token + one-time approval tokens                        (Authorization: Bearer …)
   ├─ authorized project folder ONLY (MCP_ALLOWED_ROOT)
   ├─ allow-listed commands: pytest, docker compose up/down/ps/logs
   └─ host Docker Engine  ── runs the PROJECT's own compose services
 Ollama (optional, GPU) :11434  ◀────────────────────────── backend (OLLAMA_BASE_URL)
```

* The MCP server runs **on the host**, not in a container, because it must reach the
  project folder you authorize and your host's Docker Engine. Containers do **not**
  get host files or the Docker socket mounted.
* The backend connects with the official MCP Python SDK (`mcp==1.26.0`) over
  **Streamable HTTP**. A `stdio` transport is also supported when the backend itself
  runs on the host (`MCP_TRANSPORT=stdio`, `MCP_STDIO_COMMAND=...`).

## Tools and resources exposed

| Tool | Kind | Approval |
|---|---|---|
| `project_summary`, `list_directory`, `read_file`, `find_files` | read | no |
| `preview_write` (returns diff + content digest, never writes) | read | no |
| `list_commands` | read | no |
| `write_file(path, content, approval_token)` | write | **yes** — token bound to path + SHA-256 of content |
| `run_command(command_id, approval_token)` | execute | **yes** for `run_tests`, `compose_up`, `compose_down`; no for `compose_ps`, `compose_logs` |
| Resources: `project://tree`, `project://file/{path}` | read | no |

## Security model (least privilege, defense in depth)

1. **One authorized root.** Every path is resolved and must stay inside
   `MCP_ALLOWED_ROOT`; `..`, absolute paths, drive letters and symlink escapes are
   rejected. A filesystem root (`/`, `C:\`) cannot be authorized.
2. **Protected files** are never readable or writable, even inside the root: `.env*`
   (except `.env.example`), `.git/`, `.ssh/`, `*.pem`, `*.key`, credentials, DB files.
   Writes into `node_modules`, `.venv`, `.next`, `build`, `dist` are refused.
3. **No shell.** Only allow-listed commands with fixed argument lists, `shell=False`,
   a timeout, the project folder as working directory, a scrubbed environment (no
   J.A.R.V.I.S. secrets passed to children) and redacted, truncated output.
   An optional override list (`MCP_COMMANDS_FILE`) must live outside the project.
4. **Human approval is enforced by the server, not just the UI.** The backend mints a
   one-time HMAC token (`JARVIS_APPROVAL_SECRET`) only when a person clicks *Approve*.
   The token names the exact action, expires after 120 s and cannot be replayed, so a
   misbehaving client or model cannot write files or start services on its own.
5. **Authenticated transport.** The HTTP endpoint requires `Authorization: Bearer
   <MCP_AUTH_TOKEN>` (constant-time compare). Ports bind to loopback by default.
6. **Secrets stay out of Git and logs.** `.env` files are git-ignored; secrets are
   generated by `scripts/generate_secrets.py` and never printed; log records and
   command output pass through redaction.
7. **Audit trail.** Every proposal, approval, rejection and read-only command is
   appended to `/app/data/audit.jsonl` (Docker volume `jarvis-data`) and shown in the UI.

The MCP server runs with **your user's OS permissions** — it cannot do anything you
couldn't, and it does not bypass Windows/macOS/Linux access controls. Authorize a
project folder, never your home directory.

## Setup

1. Generate matching secrets and choose the folder J.A.R.V.I.S. may access:
   ```
   python scripts/generate_secrets.py --root "C:\Users\you\projects\demo-project"
   ```
   For the demo you can authorize a **copy** of `sample-data/demo-project`.
2. Install and start the server (keep this terminal open):
   ```
   python -m venv mcp-server/.venv
   mcp-server\.venv\Scripts\pip install -r mcp-server\requirements.txt      (Windows)
   scripts\start-mcp-server.ps1
   ```
   macOS/Linux: `mcp-server/.venv/bin/pip ...` and `scripts/start-mcp-server.sh`.
3. Host binding:
   * **Docker Desktop (Windows/macOS):** keep `MCP_HOST=127.0.0.1`.
     `host.docker.internal` reaches the host's loopback.
   * **Linux Docker Engine:** loopback is not reachable from containers. Set
     `MCP_HOST` to the docker bridge gateway (`docker network inspect bridge -f
     '{{(index .IPAM.Config 0).Gateway}}'`, usually `172.17.0.1`). The compose file
     maps `host.docker.internal` to that gateway via `host-gateway`.
4. `docker compose up --build`, open the UI → **Workspace (MCP)**. The status line
   should read *connected (http)* with 8 tools and the project name.

Optional: `mcp-server/claude_desktop_config.example.json` shows the same server
registered in an MCP host such as Claude Desktop over stdio. Writes there still
require approval tokens, so they will be refused — by design.

## Troubleshooting
| Symptom | Fix |
|---|---|
| UI: "Cannot reach the MCP server: ConnectError" | Server not running, wrong `MCP_HOST` (Linux), or firewall blocks port 8765 |
| "…401…" / unauthorized | `MCP_AUTH_TOKEN` differs between `.env` and `mcp-server/.env` |
| "Approval token signature is invalid" | `JARVIS_APPROVAL_SECRET` differs between the two files |
| `run_tests` says pytest not found | Install `mcp-server/requirements.txt` into the venv used to start the server |
| `compose_up` fails | Docker Desktop must be running on the host; the project needs a compose file |
